# Phase 00 — adversarial pre-review

Written 2026-11-16, **before any implementation**, against
`CAPYWAKE_NEW_ARCHITECTURE_PLAN.md` and `CAPYWAKE_LEGACY_AUDIT.md`.

Mandated by `00_AGENT_MASTER_PROMPT.md` ("perform a critical PRE-PHASE REVIEW
and correct the plan before coding") and
`03_DOCUMENTATION/05_PHASED_EXECUTION_AND_CRITICAL_REVIEWS.md` step 4.

Findings are classified **High / Medium / Low**. Per the legacy discipline
inherited here, every finding is **applied** or marked **invalid with a
one-line reason**. "Deferred" is not an outcome.

---

## HIGH-1 — "1:1 fidelity" is being promised against art that cannot be reproduced

**The attack.** The plan says the screenshot comparison is "exact" because the
viewport matches. That conflates *viewport* with *content*. The reference PNGs
were generated by an image model. They contain things Flutter cannot reproduce
from the supplied assets:

- The Home hero in `01_HOME.png` is **not** `today_integrated.png`. I compared
  them: the mockup's capybara wears a blue nightcap and hugs a yellow duck;
  `today_integrated.png` has no cap and no duck, and the bedding and camera
  framing differ. The mockup hero was a separate generation.
- `02_ALARMS.png`'s four row thumbnails are bespoke per-alarm vignettes
  (sleeping, dumbbells, backpack, headphones) rendered in a matching meadow
  frame. The mascot library has poses that are *close* (`sleeping_blanket`,
  `lifting_weights`, `walking_backpack`, `music_headphones`) but they are
  cutouts on transparency, not framed vignettes.
- The wordmark "CapyWake" is a rendered lettering treatment, not a font we have.

So a literal pixel diff will never pass, and a plan that implies it will is
setting up either a false "done" or an infinite loop.

**Severity: High.** It is the owner's primary stated requirement, and the plan
currently has no honest definition of success for it.

**Applied.** The revised plan replaces "1:1" with a **two-tier fidelity
contract**:

- **Tier A — structural fidelity, binding and measurable.** Layout geometry,
  proportions, palette, type scale/weight, corner radii, control shapes and
  states, and art *placement* must match the reference within a stated
  tolerance (±4 pt on major block positions at 393×852). This is checked by
  side-by-side capture and is a pass/fail gate.
- **Tier B — illustration fidelity, best-effort and declared.** Where the
  mockup's art does not exist in the asset package, we use the nearest supplied
  asset and **record the substitution** in that screen's deviation log. We do
  not generate new art, and we do not pretend the substitute is the original.

Phase 02 opens with a written asset-to-mockup mapping per screen so these
substitutions are known before the screen is built, not discovered after.

Additionally: the wordmark is treated as an **asset** (a cropped PNG from the
reference header), not as a font match, since no supplied font reproduces it.
Checked for licence: it is the owner's own generated art, so bundling is fine.

## HIGH-2 — Phase ordering lets Home ship before an `Alarm` type exists

**The attack.** The plan runs 02 Home → 03 domain → 04 Alarms. Home's entire
reason to exist is the **next-alarm card** showing `7:00 AM / Mon – Fri` with a
working toggle. Building it before `Alarm` exists means Home gets a throwaway
view-model, then gets rewritten in phase 04 — and the rewrite is exactly the
"retrofit an existing screen" motion that failed last time.

**Severity: High.** It reintroduces the failure mode the rebuild exists to
avoid.

**Applied.** Phases reordered. The domain moves **before** the first screen:

```
01 Foundation (tokens, design/, router, shell, art pipeline, l10n)
02 Domain + persistence   (was 03)
03 Home / Today           (was 02)
04 Alarms list + Add/Edit
05 Alarm engine + reliability
...
```

Home is then built against the real `Alarm` model and a real repository backed
by an in-memory Drift database. No throwaway view-model, no rewrite.

## HIGH-3 — Nothing in the plan actually captures a screenshot

**The attack.** The plan says "boot the simulator, capture at that viewport" as
if it is free. It is not. `flutter screenshot` requires a running app and gives
a device-resolution PNG; the legacy repo captured **zero** screenshots across
40 phases precisely because its runner had no display. If the mechanism isn't
built and proven in Phase 01, every later phase will claim visual verification
it did not perform — which the master prompt explicitly forbids.

**Severity: High.** The entire fidelity claim rests on a capability nobody has
demonstrated yet in this project.

**Applied.** Phase 01 gains a **hard deliverable**: a working capture harness,
proven end-to-end on a trivial screen before any real screen is built.

- `integration_test/capture_test.dart` drives the app and writes PNGs via
  `IntegrationTestWidgetsFlutterBinding.takeScreenshot`.
- `tool/capture.sh <screen>` boots the iPhone 14 Pro simulator, runs the
  capture, and writes `docs/visual/<screen>/actual.png`.
- `tool/compare.dart` writes `side_by_side.png` and prints block-position
  deltas against the reference.

Phase 01's definition of done includes *"`tool/capture.sh` produced a real PNG
of the shell at 393×852"*. If the harness cannot be made to work, that is a
blocker surfaced in Phase 01 — not a surprise in Phase 03.

## HIGH-4 — The Stats mockup's numbers will leak into the widget tree

**The attack.** `05_STATS.png` shows `7 h 32 m`, `+18 min vs. last week`,
`7:20 / 7:45 / 6:58 / 7:36 / 8:02 / 7:40 / 7:34`, `6 days`, `Best: 14 days`,
`Goal 8 h`, `Avg. 94 %`, `10:28 PM`, `52 h 44 m`. Building this screen to look
right *is* building a screen full of those numbers. The most natural
implementation — hardcode them, make it look like the mockup, "wire it up
later" — directly violates the handoff's hardest content rule, and the owner
chose the **largest** Stats build (all three segments), which triples the
surface area for this leak.

**Severity: High.** The handoff calls fabricated metrics out more times than
any other rule.

**Applied.** Three mechanisms, all in place before Stats is built:

1. **Empty state is the default, not the fallback.** Every Stats widget is
   written to render the no-data state first; the populated state is the
   branch. A widget test asserts the empty state renders with an empty repo.
2. **A lint-level gate.** `tool/check_no_fake_stats.dart` greps
   `lib/features/stats/` for numeric literals in user-facing positions and
   fails the build. Added in the same phase as the screen.
3. **Demo data lives in tests and goldens only**, never in `lib/`. The
   side-by-side comparison capture is allowed to run against a seeded test
   repository — and the capture script records that it did.

## MEDIUM-5 — Four game cards on Home, zero games built, for ~10 phases

**The attack.** Home ships in phase 03. The first game ships around phase 11.
In between, Home shows Step Quest / Shake DJ / Catch the Capy / Find the
Impostor — four cards that do nothing. The plan's mitigation ("no card lies
about being playable") is a sentence, not a design.

**Severity: Medium.** A dead-end tap is a real UX defect and the owner will see
it on every run.

**Applied.** The game catalogue is a typed `core/games/game_catalogue.dart`
with an explicit `GameAvailability { playable, comingSoon, blocked }` per
entry. Home renders the rail from the catalogue. A `comingSoon` card is visibly
and semantically marked and opens a short "not built yet" sheet rather than a
broken route. `blocked` entries (Step Quest, QR Hunt — see MEDIUM-7) carry the
reason. The rail is tested with 0 playable games, which is the state it ships
in.

## MEDIUM-6 — "Settings shows only implemented features" collides with the mockup

**The attack.** `04_SETTINGS.png` shows an **Account** group: Backup & Sync
"On (iCloud)", Restore Purchases, About CapyWake v1.0.0. The architecture plan
bans auth/cloud-sync/backend as a non-goal and the handoff says show only
implemented features. So the screen *cannot* match the mockup, and the plan
does not say what goes in that space — leaving a hole that will be filled
improvisationally at 2 a.m. in phase 07.

**Severity: Medium.** Predictable, and cheaper to decide now.

**Applied.** Decided now, recorded here:

- **Backup & Sync — dropped.** It implies a backend the product will not have.
- **Restore Purchases — dropped** for now. All alarm features ship in the paid
  download (legacy rule); there is nothing to restore. If IAP is ever added,
  the row returns with it.
- **About CapyWake — kept**, real version from `package_info`.
- The group is renamed **About** and gains the two rows the product genuinely
  needs and the mockup lacks: **Reliability Checklist** and **Setup
  Walkthrough**, which the product contract requires be reachable from
  Settings.

The group keeps the mockup's exact visual treatment. Deviation logged against
`04_SETTINGS.png` as intentional, with this reasoning.

## MEDIUM-7 — Two of the ten games are blocked by a decision the plan doesn't surface

**The attack.** The plan lists "the ten games, one per phase" as if they are
uniform. Two are not: Step Quest needs step counting, and `sensors_plus` was
chosen *specifically* to avoid `ACTIVITY_RECOGNITION` (Android 10+) and Motion
& Fitness (iOS); QR Hunt needs a camera dependency that does not exist. Burying
that in the audit means it resurfaces as a surprise ten phases from now.

**Severity: Medium.**

**Applied.** Both are marked `blocked` in the game catalogue from day one, with
their reason, and are sequenced **last**. Each requires an explicit owner
decision to unblock, because each adds a store-visible permission. The Home
rail therefore shows them as unavailable rather than coming-soon. Note that
`01_HOME.png` features **Step Quest as the first card**, so this is visible on
the primary screen — logged as a deviation from the mockup, caused by a real
platform constraint.

## MEDIUM-8 — The 12 MB art budget is asserted, not computed

**The attack.** Four hero scenes at 1536×1024 PNG are ~1.9 MB *each* — 7.6 MB
before a single mascot. 29 mascots, 14 decor, 11 icons and 5 WebP loops follow.
The legacy repo hit 2.9 MB only by re-encoding and dropping the PNG frame
sequences. 12 MB may be either wastefully loose or impossible; nobody has
measured.

**Severity: Medium.** A bundle-size gate that was guessed will be either
toothless or a false blocker.

**Applied.** Phase 01 **measures before it sets the number**:

1. Import and downscale to 2× the largest on-screen render box.
2. Re-encode WebP (`-q 82` lossy for photographic scenes, lossless for
   flat-colour cutouts), compare visually at render size.
3. Record the actual total, then set the gate at **measured + 20 %** headroom.

The 12 MB figure in the plan is a placeholder and is labelled as one.

## MEDIUM-9 — No decision on how the mockup's typography is reproduced

**The attack.** Every mockup uses a rounded, heavy, geometric sans — for the
wordmark, the `7:00 AM` time, the headings. The plan's token table lists
colours but **no font**. Flutter's default is Roboto/SF, neither of which is
that face. Typography is one of the loudest fidelity signals; getting it wrong
makes every screen read as a near-miss regardless of layout accuracy.

**Severity: Medium.** It affects all five screens and is cheap to decide early,
expensive to change late.

**Applied.** Phase 01 selects and bundles a rounded geometric sans with a
licence that permits app embedding (candidates: Nunito, Baloo 2, Quicksand,
Fredoka — all SIL OFL). Selection is made by rendering the string "CapyWake
7:00" in each at the mockup's size and comparing against the reference crop.
The chosen family, its licence file and the comparison go into
`docs/visual/typography/`. The wordmark itself stays an asset (HIGH-1).

## LOW-10 — The plan says "iPhone 14 Pro 393×852" but the mockups compute to 853

**The attack.** 1847 / 2.165 = 853.1, and iPhone 14 Pro is 852. One point.

**Severity: Low.** But it will make a naive diff fail by a row forever.

**Applied.** The comparison tool scales the reference to the captured height
and reports deltas in points, tolerating ±1 pt of rounding. Documented in
`tool/compare.dart`.

## LOW-11 — `new_capywake` is not a git repository

**The attack.** It is an empty directory inside the `pets` repo. Committing
there would mix the new app into the studio repo's history, and the legacy's
"main is the only branch, commit per phase" ritual has nothing to run against.

**Severity: Low** but blocking for Phase 00's own completion.

**Applied.** Phase 00 runs `git init` in `new_capywake/`, adds a `.gitignore`,
and makes the Phase 00 documents its first commit. `pets/.gitignore` is checked
so the nested repo does not confuse the parent.

---

## LOW-12 — Settings is reachable from three tabs but has one back destination

**The attack.** The gear appears on Home, Alarms and Stats. Pushing `/settings`
from any of them and popping must return to the originating tab. With a naive
`go_router` top-level route it returns to whatever the shell last showed, which
is usually right by accident and wrong when it isn't.

**Severity: Low.**

**Applied.** `/settings` is declared outside the `StatefulShellRoute` and the
shell's branch state is preserved, so `pop()` restores the originating branch.
A router test asserts push-from-each-tab → pop → same tab, for all three.

## What this review did not find

I looked for and did **not** find problems with: the three-tab navigation
decision (the mockup evidence is unambiguous), the layer architecture
(inherited, tested, sound), the minutes-since-midnight time convention, the
read-only `SleepGateway`, or the safety rules carried over from the legacy
`CLAUDE.md`. Those stand as written.

## Outcome

12 findings: **4 High, 5 Medium, 3 Low. All 12 applied.** Zero deferred, zero
invalid.

`CAPYWAKE_NEW_ARCHITECTURE_PLAN.md` and `ai-orchestration/PHASE_TRACKER.md`
are revised accordingly. Implementation begins at Phase 01, not before.
